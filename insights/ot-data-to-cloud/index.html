Executive summary

Critical infrastructure is now a standing target. The question is no longer whether a network will be probed, but whether a probe can ever become a path.

In modern industrial and critical infrastructure environments, cyber threats are constant and evolving. Any system — directly or indirectly — can become a point of vulnerability. Power grids, substations, energy plants, dams and industrial control systems are increasingly targeted by ransomware, intrusion attempts and data exfiltration campaigns.

To address this, the unidirectional data diode provides a hardware-enforced, air-gapped solution that ensures secure, one-way data transfer between isolated networks — without exposing internal systems to any form of return communication or logical interaction.

Unlike firewalls or proxies that rely on configurable software, the diode operates through fixed, FPGA-driven logic. It allows only authorized protocols and file types while blocking all others at the hardware level — delivering deterministic, tamper-proof data flow with zero exposure.

“Data leaves. Nothing returns. The return path is not blocked by a rule that can be changed — it does not physically exist.”

Introduction

Cloud analytics wants plant data. The plant cannot afford to want anything from the cloud.

Predictive maintenance, fleet benchmarking, digital twins, energy optimisation and vendor telemetry all depend on moving process data out of the plant and into a cloud platform. The business case is rarely in dispute. The connection is.

What security teams actually object to

Not the cloud itself — the link. Connecting an OT environment to an internet-reachable service means the plant now has a route to the internet, and therefore the internet has a candidate route to the plant. The Colonial Pipeline incident is the standing illustration: OT systems were not directly breached, yet interdependency between the IT estate and operations was enough to force an operational shutdown.

Why “outbound only” is not the same as one-way

A firewall rule that permits outbound traffic still establishes a bidirectional TCP session — the response path is the connection. Command-and-control traffic has used precisely that shape for years.

Outbound-only is a configuration. One-way is a property of the hardware. The distinction matters because configurations are edited, inherited and misapplied; a missing return path is not.

Challenges

The common ways to get plant data to the cloud each reintroduce the path they were meant to avoid.

  • VPNs and reverse tunnels. A tunnel is a route. Once established, traffic flows both ways by definition — that is what makes it a tunnel.
  • Vendor remote-access appliances. Often installed for support and frequently maintained outside the IT department’s jurisdiction, repeating the contractor pattern that already undermines OT and CCTV estates.
  • Dual-homed cloud gateways. An edge device holding both an OT interface and an internet interface is a bridge whose only boundary is software.
  • Agent and firmware upkeep. Any gateway running a general-purpose operating system inside the plant inherits a patch obligation and a vulnerability feed.
  • Credential sprawl. Cloud tokens, broker certificates and API keys stored inside the OT zone become targets that justify an attacker’s effort.
  • Shared-responsibility confusion. The provider secures their platform. The route from your plant to it remains entirely yours.

“An outbound connection is still a connection. The only link an adversary cannot traverse is one that does not exist in the return direction.”

Why Terafence

Publish northbound. Accept nothing southbound.

Terafence is installed between the OT segment and the network that reaches the cloud. Side A acquires process data, files and events from the plant. Side B independently establishes the connection to the cloud service — MQTT broker, web endpoint or file target — and publishes. The two sides terminate separate TCP/IP sessions; nothing crosses end to end.

Native support for MQTT as data broker and publisher, HTTP/S upload to web servers and cloud, and SFTP means the platform receives data in the form it already expects. No change is required on the cloud side, and no proprietary agent is introduced on the plant side.

Nothing is stored inside the unit. Raw data moves through and is not retained, which removes the gateway as an exfiltration target and removes any requirement to secure data at rest within it. Terafence does not rely on cryptography to protect the exchange — it denies network access instead.

What this changes

  • Cloud credentials leave the plant. Broker certificates and API tokens live on the internet-facing side, not inside the OT zone.
  • A compromised tenant goes nowhere. If the cloud account, broker or endpoint is breached, there is no return path into the plant to exploit.
  • No operating system in the core. The FPGA core carries no OS, no MAC and no IP, so it has no patch obligation and cannot be scanned or addressed.
  • Protocol-native throughput. MQTT, HTTP/S and SFTP are carried as the platform expects, at up to 1 Gbps.
  • The air gap survives review. The isolation claim holds up to a port scan, which is what a CSO evaluation will ask for.
